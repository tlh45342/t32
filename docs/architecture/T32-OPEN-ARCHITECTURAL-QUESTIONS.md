# T32 Open Architectural Questions

**Status:** Deferred design notes  
**Purpose:** Preserve unresolved architectural questions without blocking current compiler and runtime development.

---

## 1. Condition and Status Model

T32 currently maintains four arithmetic condition flags:

- `C` — carry / no-borrow
- `Z` — zero
- `N` — negative
- `V` — signed overflow

Arithmetic instructions and `CMP` / `CMPI` update these flags.

Ordinary conditional control flow remains explicit and register-based:

```asm
jz  r0, target
jnz r0, target
```

These branches inspect the named register directly and do not implicitly consume `Z`.

### Open questions

- Should the four flags become a packed architectural `STATUS` register?
- Should guest code be able to read status with an instruction such as:

```asm
mrs r0, status
```

- Should guest code be able to restore status with an instruction such as:

```asm
msr status, r0
```

- If `MSR` is added, should it be privileged or masked?
- Which additional bits may later belong in `STATUS`?
  - interrupt enable
  - privilege or execution mode
  - exception state
  - reserved expansion bits
- How are status bits saved and restored by traps, interrupts, `IRET`, and future task switching?

### Current direction

Keep register-based branches as the primary control-flow model.

Do not redesign `JZ` or `JNZ` merely because condition flags exist.

Formalize status only when interrupt, exception, task-switching, debugger, or compiler requirements provide enough evidence.

## 2. `CMP` and `CMPI`

Current behavior is subtraction without a destination:

```text
CMP  ra, rb   -> flags from ra - rb
CMPI ra, imm  -> flags from ra - imm
```

The temporary arithmetic result is discarded. Source registers are unchanged.

### Open questions

- Are `CMP` and `CMPI` primarily:
  - arithmetic-status producers;
  - debugger-visible state producers;
  - preparation for future relational branches;
  - preparation for future status reads;
  - or instructions that may ultimately prove unnecessary?
- Should a future comparison instruction produce an explicit register result?
- Should signed and unsigned relational operations eventually use:
  - flag-consuming branches;
  - result-producing comparisons;
  - explicit register arithmetic;
  - or a combination?

### Current direction

Keep the existing instructions and document their exact flag behavior.

Let `t32-cc` provide evidence before adding or removing comparison-related instructions.

---

## 3. Multiply Result Width

`MUL` and `MULU` currently produce a 32-bit destination result.

The upper 32 bits of a full 64-bit product are not directly available.

### Open questions

- Is the low 32-bit result sufficient for the intended T32 workload?
- Should future instructions expose the upper product word?
- Possible future forms include:

```asm
mulh   rd, ra, rb
mulhu  rd, ra, rb
```

- Should signed and unsigned multiplication use different overflow conventions?
- Should carry and overflow behavior remain different between `MUL` and `MULU`?

### Current direction

Do not add `MULH` or related instructions without evidence.

Measure code generated by the compiler, runtime, libraries, firmware, and applications first.

---

## 4. Division and Remainder

`DIV` and `DIVU` currently produce only the quotient.

Remainder can be synthesized:

```asm
div r2, r0, r1
mul r3, r2, r1
sub r4, r0, r3
```

### Open questions

- Is synthesized remainder acceptable for T32?
- Should future instructions add:

```asm
rem   rd, ra, rb
remu  rd, ra, rb
```

- Should quotient and remainder ever be produced together?
- Are current signed division semantics explicitly documented as truncation toward zero?
- Are divide-by-zero and signed-overflow traps fully specified?

### Current direction

Accept the longer synthesized sequence for now.

Use compiler-generated `%`, library code, and instruction-frequency studies to decide whether dedicated remainder instructions are justified.

---

## 5. Shift Semantics

T32 provides:

```asm
shl
shr
sar
```

### Open questions

- How are shift counts greater than 31 handled?
  - masked to five bits;
  - rejected;
  - treated as zero;
  - or otherwise defined?
- What happens to carry when the shift count is zero?
- Which flags are preserved, cleared, or recomputed?
- Are register and immediate shift forms required separately?

### Current direction

Audit the VM implementation and tests, then document the exact existing behavior before changing anything.

---

## 6. Memory Alignment

Byte, halfword, and word accesses require a precise alignment contract.

### Open questions

- Are unaligned halfword and word accesses:
  - supported;
  - trapped;
  - undefined;
  - or decomposed internally?
- What alignment guarantees does the ABI require?
- How should future firmware, devices, and memory-mapped I/O treat unaligned accesses?

### Current direction

Determine and document current VM behavior before the compiler begins emitting more complex data layouts.

---

## 7. Instruction Utilization Study

T32 should eventually measure which instructions are actually used.

Useful measurements include:

- single-instruction frequency;
- instruction-pair frequency;
- repeated three-to-six-instruction sequences;
- code size per C construct;
- cycle cost per C construct;
- instruction use by compiler, runtime, firmware, and applications.

### Questions this study may answer

- Are `CMP` and `CMPI` used by generated code?
- Is remainder synthesis common enough to justify `REM` / `REMU`?
- Is upper-word multiplication common enough to justify `MULH` / `MULHU`?
- Are some existing instructions effectively unused?
- Are repeated instruction sequences revealing a genuinely missing primitive?

### Current direction

Do not remove or add instructions based only on intuition.

Let measured compiler and system workloads provide evidence.

---

## 8. Guiding Principle

T32 favors explicit operands, explicit data flow, and understandable behavior.

Hidden architectural state should be minimized, but state required for arithmetic, exceptions, interrupts, debugging, and execution-context restoration must be preserved and defined.

Open questions are not forgotten questions.

They are intentionally deferred until implementation experience and measurement provide enough evidence for a durable decision.
